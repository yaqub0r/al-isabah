# Bounded source-record correction (issue 89)

This producer workflow takes an independently pinned, completed gated history and one reviewed rebased obligation seed. It never launches a worker or authorizes a corpus export. The saved historical verifier authenticates the final proposal, ledger, gate, repair and report before any new request is built. Keep the full thirteen-record packet locked for graph validation. The only default write target is the source record named in the reviewed scope; cross-record changes require an exact declared reference and still need validation.

Prepare the scope from packet identities, not a candidate translation: source ordinal, legacy ID, all owned units (including structural headings), inherited read-only context, the unresolved target obligation IDs, and any declared cross-record references. `preview_context` plus `request(..., preview=True)` gives metadata for review, with `authorizable:false`. `seed_candidate` copies the original twenty-obligation seed and replaces only its baseline output and origin report pins. A trusted review must mark its status `reviewed_for_gate` without changing the obligation rows before calling `context`. This rebase makes new progress relative to the repaired final graph, so previous additions do not count again.

After the runner, accounting schema, tests and this runbook are reviewed and committed, generate `request(ctx, commit)`. The exact request binds committed LF source hashes, the directory, full source and packet, partition, profile and output schema, final history lineage and repair, scope, rebased seed, method and three-worker cap. A new user-origin decision must contain this exact request. Earlier issue-89 decisions do not authorize this correction.

Run the stages in order: source-anchored extraction, independent critique, adjudication. For each stage, persist the exact `stage_input` under `<stage>.input.json`, call `reserve_once`, then launch a fresh GPT-6 Sol/high worker. Bind the host log with `bind_once` even if the attempt fails or its terminal state is unknown. That slot is consumed; this workflow has no retry or fourth slot. A completed worker can submit the stage proposal and sidecars for `capture`; save the resulting receipt without changing any input or evidence bytes. `report` replays the three completed stages and retains all four earlier launch rows plus the three new ones.

The accounting sidecar partitions every owned source span into exact contiguous character ranges, each bound to its UTF-8 SHA-256. Mark each segment as graph-represented, qualified uncertainty with a finding, unresolved with a reason and finding, structural, or nonsemantic. Give every target report one route row and attach it to anchored atoms. The independent critic must verdict every atom and route, check omissions, conflated speakers or reports, unsupported inference, identity, qualifications, and any witness need. Deterministic partition and route coverage are necessary checks, not proof of semantic exhaustiveness. Adjudication may set `recordComplete` only when it retains the reviewed accounting unchanged apart from that flag, the critic reports no missing or unsupported material, both known obligations resolve, and the target graph meets the repository's established completion conditions: checked review axes, no blocked owned span, substantive open concern, unresolved nonclaim review, or applicable blocking finding. Only the existing exact, unchanged legacy-provenance concern classification is exempted; a changed concern or a blocking finding is not. A clean accounting review can still produce an honest partial record if graph blockers remain. A source or rights defect remains under its own fail-closed rule. Volume coverage, human review, consumer admission and public release remain unapproved.
